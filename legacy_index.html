matrix: a lazily evaluated linear algebra library

Every operation has a CPU path and a Metal GPU path. Writing an expression only builds a graph. Nothing is computed until you ask for a result, so the same graph can be compiled once and run on either device.

THE FUNCTION (USAGE SKETCH)
matrix x = matrix::rand({4});      // a leaf: no math yet
matrix a = x * x;                  // each line adds a node
matrix s = matrix::sin(a);
matrix f = s * matrix::exp(x);

f.eval();   // now the graph runs, on CPU or Metal
THE GRAPH IT BUILT
each node runs on CPU Metal GPU
ITS GRADIENT (USAGE SKETCH)
auto f = [](matrix x) {
  return matrix::sin(x * x) * matrix::exp(x);
};

auto df = matrix::grad_gpu(f, x);  // builds a new graph
matrix g = df(x);                  // same lazy machinery
THE GRADIENT GRAPH: df/dx = eˣ · (2x · cos x² + sin x²)
built by vjp rules, one per node type, so it is a graph too
THE WHOLE REVERSE-MODE RULE FOR sin, FROM primitives.cpp
class SinPrimitive : public Primitive {
  // ...eval_cpu / eval_metal...

  std::vector<matrix> vjp(matrix& grad_out) override {
    return { grad_out * matrix::cos(input) };  // d/dx sin(x) = cos(x)
  }
  matrix jvp(std::vector<matrix>& tangents) override {
    return tangents[0] * matrix::cos(input);   // forward mode
  }
};
  • Graph, not eager. A matrix is an edge and a Primitive is a node. The graph is built once, compiled once, and run many times.
  • Both AD modes. Every primitive implements vjp (reverse) and jvp (forward): matmul, broadcast, reshape, slice, pad, concat, cross product, max/min and trig.
  • JAX-style functions. Gradients are new graphs, so there is no .backward() and no mutable .grad.
  • Live parameters. A slider owns a one-element leaf in the graph. Moving it marks only the dirty path for re-evaluation, into the same buffers, and ten ticks between two frames become one recompute.
  • Metal kernels. Elementwise, broadcast, matmul, 1D/2D/3D convolution, reductions and GPU random numbers, plus operator fusion and a JIT path that reuses compiled graphs.
  • Engineered carefully. About 20,000 lines across matrix.h, Matrix.mm and primitives.cpp, a two-count memory model for shared buffers, and memory bugs found and fixed with ASan and UBSan.

Ports of published models to Apple's MLX framework, each checked against the original. A fourth, the SalsaNext segmentation network, is in the driving section below.

Depth Anything V2 on MLX

Single-image depth estimation, ported layer by layer from PyTorch to MLX: the DINOv2 encoder and the DPT depth head. A converter turns the official .pth weights into MLX .npz files, and verify_port.py compares outputs with the PyTorch model.

It runs on images, video and a live webcam, and can turn a frame into an interactive 3D point cloud.

From predicted depth to 3D

The depth map is a distance for every pixel, so each pixel can be pushed out into space and coloured from the photo. That turns one webcam frame into a point cloud you can orbit.

MediaPipe hand tracking, rewritten in C++ on MLX

Google's hand pipeline normally runs on TensorFlow Lite. I wrote a transpiler that reads the .tflite models and generates the equivalent MLX C++ forward pass, then reimplemented the tracking logic around it: rotated crops, anchor decoding, non-max suppression, IoU checks so one hand never gets two trackers, and One Euro smoothing.

The result is 21 hand landmarks per hand from a webcam, with no TFLite at inference time.

Autonomous driving

Segmenting a lidar scan in 26 milliseconds

For our Smart India Hackathon 2026 entry (DRDO problem SIH26053, adaptive-resolution 2.5D lidar mapping) I ported the SalsaNext segmentation network to MLX C++, fed its output into a foveated 2.5D grid, and measured the whole pipeline on SemanticKITTI.

lidar scan→ range image 64×2048×5→ SalsaNext (MLX C++, Metal)→ class per point→ foveated 2.5D grid→ tiles in the renderer
Whole pipeline26.4 ms / scan37.9 FPS. The sensor produces 10 scans a second.
SalsaNext inference17 ms / scan6.7M parameters, 64×2048 input, on the GPU.
Accuracy, 3 groups88.3 %Terrain, static, dynamic. 84.0% across all 20 classes.
Grid memory7.3 MB26× less than a uniform 5 cm grid, 437× less than 3D voxels.
Port correctness3.2e-6 max diffAgainst the PyTorch output, with 100% matching class labels.

Measured on 500 scans (58.9 million labelled points) of the SemanticKITTI validation sequence. Mean IoU is 46.3%, below the published figure of about 59, because this run used only 500 scans and skipped SalsaNext's optional KNN post-processing.

One hallway, three views

Recorded on an iPhone. The real hallway, the LiDAR depth map, and the point cloud where GPU RANSAC has found the floor plane and painted it green. The depth view is drawn on the phone and its counter reads about 60.

  • Foveated grid. Four nested square rings with cells that grow from 5 cm within 10 m to 40 cm out to 100 m. Rings meet on whole-cell boundaries, so every point lands in exactly one cell: 610,000 cells instead of 16 million.
  • Written from the paper up. The checkpoint is a legacy pickle that also carries optimiser state, so I audited it without executing it, then converted the weights and rebuilt the network. Tests cover the range projection, the label decoding, the grid tiling and a synthetic sequence.
  • Phone lidar too. The same grid takes depth from an iPhone, unprojected with the camera intrinsics. SalsaNext does not transfer to that data, so there the floor comes from GPU RANSAC constrained by the phone's gravity vector and obstacles come from plane clustering.
  • QuantumStream. Streams live tensors from the iPhone to the Mac over TCP or chunked UDP. A depth map, an RGB image and the camera intrinsics travel together as one frame.

Applets and control panel

Each prototype is a function that reuses the engine, so a new idea does not need a new Xcode project. Sliders, toggles and a native panel for macOS and iOS come with it. Applets so far include a per-pixel differential equation solver, a gravity particle simulation and the eight-million-point renderer above.
